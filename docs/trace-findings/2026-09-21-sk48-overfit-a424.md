# sk48 overfit diagnostic on gx10-a424 — BF16 arm

**Status: IN PROGRESS — results sections are placeholders until the artifacts land.**

## 0. What this test is, and why it is clean

`sk48` ("Skewer Kebabs") is one of seven public games the 27B scores a flat 0.00 on. The
Boss's framing is the whole point of the diagnostic: this game is dead easy for a human, and
it is **fully deterministic** — no randomness, the entire board visible from the first frame.
A player can look at the initial board of each level, form a complete plan, and execute it.
There is nothing stochastic to blame a failure on.

So the question this arm asks is narrow and answerable: **load the model up with the complete
rulebook, in its own plain words, and can it still not clear a level?** A failure here is not
a perception-under-uncertainty result or a bad-luck result. It is a reasoning result.

Overfitting is the intent, not a flaw. The model is told the game's name and its full
mechanics up front — exactly the variable a benchmark holds out. **No score in this document
is comparable to any benchmark arm.**

## 2. What was injected

The treatment is built from the Boss's own write-up —
`82deutschmark/arc-explainer:shared/arc3Games/sk48.ts` — not from a fresh reading of the game
source. It is delivered through the **existing** oracle-rules mechanism
(`ARC3-Inference/inference/agent/oracle_rules.py`, selected by `ARC3_ORACLE_RULES_DIR`), which
puts the block first in **every** user turn and strips it from retained history so exactly one
live copy sits in context. Nothing about that mechanism was reinvented for this run.

Rulebook file: `datasets/explainer-games/rulebooks-sk48-overfit/sk48.txt`, **9,537 bytes**,
rendering to a **9,611-character** injected block (confirmed in the run log:
`oracle rules loaded state_path=sk48-d8078629_p0_tool_runtime_state.json block_chars=9611`).
It is the same byte-identical file the Mac Mini arm uses.

Beyond the stock rendered rulebook it carries:

- **The game's name, up front.** `THIS GAME IS CALLED "SKEWER KEBABS" (game code sk48). It has
  8 levels.` The stock system prompt opens *"You are a coding agent solving a grid-based puzzle
  game"* and never names the game at all.
- **The Boss's plain framing.** You are holding a meat skewer; the colored boxes are pieces of
  meat; the strip below the board **is the win condition**, the order the kebab is wanted in.
  You cannot walk up to a piece and have it appear on the skewer — you **push it against
  something that will not move** (board edge, wall, or an already-stuck piece) and the skewer
  slides through it. That is the single most important mechanic in the game.
- **Undo as load-bearing.** To get a piece *off* the skewer you use Undo (ACTION7). This is a
  push-block puzzle: pushing is one-directional and retracting does not pull a pushed piece
  back, so a bad extension can permanently scramble the board. Undo is the only thing that can
  take a push back, it is free, and it can be pressed repeatedly back to the level start.
  *"When a plan goes wrong, UNDO; do not try to play your way out of it."*
- **Later levels need pieces moved out of the way first**, and on **level 3** you knock a kebab
  back off the skewer to pick the pieces up again in the order the reference wants.
- **An explicit instruction to exploit determinism**: study the initial board of each level and
  commit to a full plan before acting.
- Per-level notes for levels 1–8 as the Boss wrote them today, including level 7 (both skewers
  need the one green) and level 8 (pink cannot reach the bottom, purple has to fetch the green).

## 3. What was REMOVED

One line was deleted from `ARC3-Inference/inference/agent/prompts.py`, `VISUAL_GAME_ADDENDUM`:

> "A common failure mode is to mistake a segmented edge bar for clickable puzzle pieces. If a
> repeated strip of small blocks sits flush against the top, bottom, left, or right border and
> actions only change that strip while the interior board stays the same, classify it as
> HUD/timer state, not as an object to click through segment by segment. DON'T DO THIS!"

In sk48 that strip **is the win condition** — it is the reference skewer showing the wanted
colour order. The stock prompt was actively telling the model to ignore the goal. Deletion
confirmed on the a424 tree: `grep -c "DON'T DO THIS" ... prompts.py` → `0`.

This deletion is part of the treatment and applies to **both** a424 arms equally, so it does
not disturb the base-vs-adapter comparison.

Two things worth recording because they were not obvious:

- **`--gpu-memory-utilization` is capped at 0.62 on purpose.** GB10 memory is unified; the
  default 0.9 would claim ~109 GiB and the kernel OOM killer would take bystander processes
  with it. OpenMind had a llama.cpp CPU job on this box throughout, and it survived.
- **vLLM is not what parses the tool calls.** This model emits
  `<tool_call><function=name><parameter=x>…` markup, which vLLM's `hermes` parser does not
  recognise (verified by smoke test: `tool_calls` came back null with the markup sitting in
  `content`). The harness's own `_recover_tool_calls_from_markup` in `tool_agent.py` recovers
  it. That is the same path the Mac Mini's LM Studio run takes, so the arms remain consistent.
- Python was relaxed from `==3.12.12` to `>=3.12,<3.13` in the local copies of
  `ARC3-Inference/pyproject.toml` and `tufa-arc-agi-framework/pyproject.toml`; a424's system
  interpreter is 3.12.3. No dependency versions were changed.

### 4.1 Throughput — a hard constraint on this box

BF16 27B on GB10 generates at **~3 tokens/s** measured at the server (`Avg generation
throughput: 3.1 tokens/s`, GPU at 96%). That is bandwidth-bound and expected: ~55 GB of
weights against GB10's memory bandwidth leaves no headroom at batch 1. It is a hardware fact
about this arm, and it bounds how many observe-plan-act turns fit in any wall-clock budget.
**It is reported separately from the model's behaviour on purpose** — see §6, where a whole
turn was spent on segmentation dumps without acting. That is not a slow box; that is a choice.

### 4.2 The round-3 adapter, and how arm 2 was built

`/home/son/arc3-round3/ckpt/adapter-step168`, per brief §7. A final `adapter/` (≈step 178,
89 records × 4 epochs ÷ 2 accum) also exists; step168 is the checkpoint the brief named and is
what produced arm 2's number. r=16, alpha=32, dropout 0, no rsLoRA → scaling 2.0.

**The adapter never saw sk48.** `ckpt/train_report.json` lists the round-3 corpus as 89 records
over 12 games — `bp35 cd82 cn04 dc22 ft09 g50t ka59 lp85 ls20 m0r0 r11l s5i5`. sk48 is not
among them, so arm 2 is a genuine transfer test, not memorisation. This is also the first time
any game has been played with this adapter loaded at all: round 3's held-out eval was scored
on the wrong yardstick, so **no task-success signal has ever come out of it before this run.**

**The adapter was merged into the weights, not served via `--enable-lora`.** Two reasons, both
load-bearing:

1. It targets `linear_attn.in_proj_qkv`, `in_proj_z` and `out_proj` — the **GDN
   linear-attention** projections of this hybrid architecture (confirmed from the adapter's own
   tensor names). vLLM's LoRA path covers standard attention projections; serving natively
   would have silently dropped most of the trained deltas and produced a wrong number rather
   than a degraded one.
2. Merging keeps brief §1 honest: arm 2's server config is byte-identical to arm 1's apart from
   the model path.

`peft.merge_and_unload()` was not usable — this checkpoint is `model_type: qwen3_5`, which the
installed transformers does not register (`AutoConfig.from_pretrained` raises
`KeyError('qwen3_5')`). The merge was done instead by streaming the safetensors shards
(`/home/son/arc3-sk48-overfit/merge_lora_stream.py`), applying `W' = W + 2.0 · B @ A` in
float32 and casting back to bfloat16, one ~4 GB shard at a time so it could not OOM the box
while vLLM held ~75 GiB. Verified after the fact: **208 / 208** adapter targets found and
merged, 18 shards in and 18 out, byte size identical at 55,563,006,776, tensor count identical
at 1,199, and every non-weight file (config, tokenizer, chat template, preprocessor) copied
across.
