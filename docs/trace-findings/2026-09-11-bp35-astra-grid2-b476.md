## Finding 1 — the turn-2 `LEFT?!` is a vision-grounding failure, not a stale frame

Turn 2 opens with:

> The image shows the player moved LEFT?! In the new image, the sprite appears at around
> x=85/256*64 ≈ 21... hmm, previously at ~ (19-22). Let me diff frames.

It then spends 5 tool calls and 2,964 characters of thinking establishing what actually
happened, and gets there:

> the player sprite moved from cols ~19-22 to cols ~25-28 → 6 columns to the RIGHT

**The image was correct and current.** The trace labels the attached frame
"Current settled frame (attached to Qwen)", and the sprite in it is at cols 26–28 —
the correct post-action position. Verified against the raw board arrays:

| | sprite col range |
|---|---|
| before `RIGHT` | 20–22 |
| after `RIGHT` | 26–28 |

At upscale 4 the board is 256 px wide, which matches the model's own divisor, so it had
the scale right. Columns 26–28 are pixels 104–115. It estimated x=85. **It misplaced the
sprite by roughly 20 pixels — five columns — and 85 px happens to land on the position
the sprite occupied before the move**, which is what made the misread read as "didn't
move / moved left".

Each cell is 4 px. A three-cell sprite is 12 px. There is nothing in a `plain`-style
render to anchor a column estimate against, so this is not a lapse; it is the expected
accuracy of eyeballing a coordinate in that image.

`vision_context.py` already contains an `outline` renderer built for exactly this: it
draws row/column tick labels in a margin every 8 cells, and its docstring says the labels
"tie what the model sees to the row/col coordinates MOUSE actions use".
`current_grid_image_style()` returns `plain` unless `MULTIMODAL_STYLE=outline` is set.

**Caveat:** the trace does not record this run's `MULTIMODAL_STYLE`, and the catalog
entry's `harness` field is empty, so the style is not directly confirmed. The model's own
arithmetic — dividing by 256 with no margin offset — is consistent with `plain`, since
`outline` adds a 26 px margin on each side. Worth confirming against the run config
before treating the env var as the fix.

## Finding 2 — 53 of 60 turns rebuild their own scaffolding

The Python sandbox does not persist between turns, so every turn re-defines the helpers
it needs before it can look at anything.

| helper | turns that re-define it |
|---|---|
| `gf` (parse `current_frame.ascii` into rows) | 28 |
| `bbox` / `bb` (locate the sprite) | 26 |
| `rle` (run-length view of a row) | 10 |
| `bub`, `runs`, `sig`, `g`, others | 18 |

53 of 60 turns re-define at least one function. This is the single largest recurring cost
in the trace and it buys nothing — the helpers are the same each time.

A persistent per-game namespace (or a small standard library preloaded into the sandbox:
sprite bbox, row RLE, frame diff) removes it.

exactly 64 characters; `format_grid_ascii` does not trim. One line in the system prompt
stating the row width is fixed and untrimmed retires this.

## Appendix — the board encoding is expensive, and the character choice is why

Separate from this trace but the same subsystem. `ARC_COLOR_CHARS` in
`inference/utils/grid_utils.py` is `WwgGcBMPRbSYOrNp`. Under BPE the cost of a board is
dominated by how well *runs of the same character* merge, and that varies enormously by
which character it is. Measured on a synthetic 64×64 board with a realistic colour mix:

| scheme | tokens | vs current |
|---|---|---|
| `WwgGcBMPRbSYOrNp` (current) | 1,900 | 1.00× |
| `ZYXWVUTSRQPONMLK` (ordinal, descending) | 2,195 | 1.16× |
| `.-=#*/_+MPRbSYON` (symbols on background/greys) | 1,690 | 0.89× |
| `.-=#*/_+~%Xaflo:` (all symbol) | 857 | 0.45× |

Summed over the run lengths a 64-wide board produces, `*` `#` `.` `-` `=` `/` `_` cost
7–8 tokens where `S` and `W` cost 98. Assigning the cheap characters to the colours that
fill the most cells is worth more than half the board's tokens.

Two caveats. The measurement uses tiktoken `o200k_base` as a stand-in; Qwen3.8-Flash-Next
uses a different tokenizer, so the mechanism transfers but the numbers do not — re-run
against the real one before changing `grid_utils.py`. And an ordinal mapping is worse,
not better, which is the counterintuitive part: BPE does not care about alphabetical
order, only about which repeated sequences are in the vocabulary.

Bench script: `scripts/ascii_symbol_token_bench.py`.

## A note on the case convention

Also in `ARC_COLOR_CHARS`: `W`/`w` is white vs light grey, `g`/`G` is grey vs dark grey,
`r`/`R` is dark red vs red — three different rules for what case means. Then `B`/`b` is
**black vs blue** and `P`/`p` is **pink vs purple**, which are not variants of each other
at all. On a board that is mostly `B`, the player can be a single `b`.
