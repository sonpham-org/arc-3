# Auto FlashInfer MoE source audit checkpoint

This is the preserved, incomplete read-only audit of the pinned Python export. No numerical patch was made. The task was interrupted before the routing factory and opaque FlashInfer reduction implementation were fully inspected; this is not a claim that those paths are deterministic or faulty.

The active class is `FlashInferExperts` in `vllm/model_executor/layers/fused_moe/experts/flashinfer_cutlass_moe.py`. Its NVFP4 path views packed weights as int64 and weight block scales as int32; `apply()` passes preselected expert IDs, routing weights, input scales, six quantization tensors and explicit output storage into `flashinfer_cutlass_fused_moe`. The inspected call provides no deterministic-reduction parameter. The class selects `TopKWeightAndReduceNoOP`, so adding a vLLM-side finalize reduction option would not by itself change the fused backend's reduction. This does not establish whether its underlying API has an unexposed option.

First-input NVFP4 quantization occurs before that fused call through `prepare_finalize/no_dp_ep.py` and the previously audited `_custom_ops.scaled_fp4_quant`; the swizzled scale allocation is zero-initialized. No confirmed uninitialized first-input scale defect was found. Intermediate activation quantization, sparse expert scratch and reduction occur within the fused FlashInfer operation and remain unverified from this export. Do not infer that inactive experts read unwritten memory solely because some buffers use `empty()`.

`VLLM_BATCH_INVARIANT` is a broader backend-selection control, not a confirmed narrow deterministic-reduction flag for the current FlashInfer implementation. `FlashInferExperts` does not advertise batch invariance, so enabling it may exclude this backend. Sorted-top-k handling exists elsewhere in bias/grouped router code, but the exact router selected for this model was not yet established by this audit; those branches should not be reported as active evidence.

The native CUTLASS synthetic microprobe subsequently passed all model-shape cases, including 6144 input tokens. That supports compiled-kernel viability for its tested synthetic values. It neither validates FlashInfer's different fused implementation nor resolves the full-model native CUTLASS startup failure. See `kernel-results/kp1/` and `numerical-backends.md` for the separately preserved evidence.
